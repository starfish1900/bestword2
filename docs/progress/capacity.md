# Local multiplayer capacity evidence

These are completed local executions on a Windows 11 x64 machine with an Intel Core i7-13700, 24 logical CPUs and approximately 16 GB RAM. Two separate Node 24.14.0 API processes and one worker shared the machine with the load driver, PostgreSQL 18.4 and Redis 7.2.16. No CPU quotas were applied. This is not a Render benchmark, a Valkey 8 execution, or evidence that the proposed $64 base configuration or a $100 monthly budget supports the tested load.

The driver uses real authenticated WebSocket connections and legal game commands through the production server. Accounts, sessions and active fixtures are seeded; signup, lobby admission and countdown are excluded. Completed games are replaced with fresh active games so the active-game count remains steady. Functional tests cover those excluded flows separately. Reproduction instructions and workload limitations are in [the load-driver guide](../../tools/load/README.md).

The two legacy healthy runs omitted the browser's periodic revision-sync traffic. Their conservative baseline rates above are calculated as `(accepted commands - sum of offered burst commands) / recorded duration`; burst traffic cannot improve that lower bound. The hour completed all 59 requested 100-command bursts. Its older duration included final command draining, and its older gate implementation did not independently establish each viewer's freshness. It establishes sustained healthy command processing, durable acknowledgements and substantial aggregate fanout under that workload.

The strict short run added staggered revision sync every eight seconds: 17,842 sync requests, of which 17,797 were unchanged responses. It separately counted 5,999 baseline commands and a fully accepted 100-command burst. All 1,200 current viewers received the final database revision through `game:update`, and all 1,800 viewer checks across 150 retiring games received their terminal push. No subscribe, command or sync acknowledgement was counted as push delivery. Push latency p95/p99 was 7/147 ms, using 1 ms histogram bins. Coalesced latest snapshots do not establish delivery of every intermediate revision.

Format-version-2 gates require the requested offered-load duration, initial/final/minimum socket targets, baseline throughput with an explicit 5% tolerance, the expected number of completely accepted bursts, service p95 below 250 ms and p99 below 750 ms, no application/privacy/disconnect errors, viewer convergence and exact durable verification. Reduced-duration runs retain `fullPreset: false`. A passing two-minute run is not a passing one-hour sync-inclusive preset.

The corrected five-minute scale trial maintained 5,000 active games and all 12,500 sockets, accepted exactly 75,000 baseline commands plus four complete 100-command bursts, and performed 465,330 revision syncs. All 12,500 viewers reached their final revision through pushes, with push p95/p99 of 20/72 ms. It verified all 75,400 command receipts and 5,000 game snapshots. The action mix included 58,749 placed words, 16,626 NO_WORDS actions and 25 permanent PASS actions, but no game reached completion during this short trial; it therefore does not establish game-recycling behavior at that scale.

For that five-minute scale workload, API RSS peaked at approximately 928 MB per process; their measured average CPU use was approximately 0.68 cores each. The worker peaked at 248 MB and averaged 0.14 cores. Sampled Redis memory peaked at 9.62 MB, free host RAM remained above 2.57 GB, and sampled maintenance-check lag peaked at 103 ms. Deadline samples showed no overdue deadlines; the trial did not intentionally create clock-expiry or outage pressure. Approximately 1.37 GB of application-level incoming payload was observed. Every child exited successfully and isolated fixture cleanup completed.

## Defects identified by these tests

The initial 1,200-socket failure exposed a Redis client queue limit while queuing heartbeat `MULTI` commands. A partial transaction could leave subsequent replies as `QUEUED`, corrupt presence interpretation and produce false results. The corrected implementation uses bounded atomic Lua heartbeat batches, an appropriate client queue limit and defensive recovery. The failed report is preserved instead of being replaced with the corrected result.

The first 5,000-game attempt exposed a different connection-startup race: heartbeat collected session hashes, awaited a database query, then iterated the live socket set. Connections added during that await were absent from the validation result and could be disconnected. This was a server-initiated disconnect after successful connections, not evidence of Windows ephemeral-port exhaustion or a throughput measurement. The server now queries and validates the same frozen socket population; a real-socket delayed-query regression reproduced the original failure and passed the correction. That failed report remains unchanged. Inspection also found that worker shutdown attempted to close an unused, unattached Socket.IO publisher, which was removed. Earlier harness versions did not check child exit codes, so their gameplay verification does not establish clean worker shutdown; the corrected scale run explicitly checked successful exits.

## Provenance and limits

Every raw report records its settings and available code provenance. Earlier reports stored only the gameplay-module checksum, which cannot identify changes in transport or health modules. The corrected 120-second legacy report therefore cannot fully establish its transport source version from hashes alone.

The one-hour run captured all compiled server/shared JavaScript and their combined SHA-256 before starting its children: `9eddba87d78b3af2f7645f5f1a3d81d03f477b61b1508a27d93556abb3cb4e83`. It predates later authentication, subscription, timeout, receipt and development-header fixes. Rebuilding files on disk did not replace modules already loaded by those children. That older harness did not record its own source checksum.

The strict short run captured combined compiled-code SHA-256 `ee48da34f5b516986026055166d58790c8f401e867a0624d099229ccc3a6210e` and combined harness SHA-256 `c59e079006462d5a06b250a6bbf09d06c087345b1dfe855bd03ba5dc73bc31cb`. Individual hashes include the server, engine, contracts, lexicon reader, load driver, observation validator, fixture helper and dependency lockfile. Subsequent diagnostic edits add startup disconnect/resource observations and fail on unsuccessful child shutdown; they do not retroactively change this tested harness.

The corrected five-minute scale run captured compiled-code SHA-256 `521d2148ece4cebe58907671db20042c58d5ff67b51da3c0da2af0e0aa9d5bd9` and harness SHA-256 `e63b025314c8f481a0ab4b32314b7894e504a46ec2bd9478a3cda543d9d091c4`. This includes the heartbeat snapshot and worker shutdown fixes. The complete per-file hashes in the raw report remain the authoritative tested-artifact record.

The hour's sampled Redis memory stayed below 4.44 MB; API RSS peaks were approximately 289 MB per process. Its approximately 24.95 GB of incoming Engine.IO payload observations are application-level counts, not a Render billable-bandwidth measurement. Commands, snapshots, pings, acknowledgements, spectator density and move frequency all affect traffic. The local machine and workload differ materially from a single paid Render API and its managed datastores.

Keep production admission at the reviewed 100-game setting until the actual paid topology passes its own load, failure/recovery and cost gates. A large local socket count alone cannot establish sustained gameplay, timely deadlines, monthly egress cost or the affordability of 5,000 games. Docker/Compose, Linux CI, managed Valkey and the Render deployment remain separate unexecuted gates on this machine; see [operations](../OPERATIONS.md).
