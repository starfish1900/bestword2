Executed evidence (2026-09-18): `npm exec tsc -- -b packages/engine` passed. `npm exec vitest -- run packages/engine/test/engine.test.ts` passed **112/112 tests**, including 1,100 randomized setup, placement and game-sequence property cases. Latest measured test run:343ms total,110ms test execution. Native test subprocess execution required sandbox escalation; permission was granted. These are rules/unit/property checks, not production throughput or infrastructure recovery evidence.

API addition: `restartRecovery(state, now, reason)` is for a newly identified infrastructure incident during an existing recovery window. It preserves frozen clocks and draws, clears readiness and the recovery deadline, and lets `beginRecovery` start a fresh120seconds once service is healthy. The server deduplicates incident IDs; repeat scans must not repeatedly reset recovery.

No network or filesystem operations occur in the engine. `dueOutcome` only returns an outcome candidate; the server establishes infrastructure health before `adjudicate`. Duplicate-command handling remains the server's responsibility.

## Service failure verification

The delegated reliability work adds bounded Redis command replies (1.5 seconds), a bounded write queue, socket replacement after uncertain MULTI execution, and atomic presence updates. The Redis library's built-in command timeout stops covering a request after its bytes are written, so an outer reply deadline is necessary for half-open connections. Adapter readers remain separate clients with longer limits for their blocking reads. Health checkpoints require the actual `PONG` response; presence requires an array of strings.

Executed after the notification-stream and batched-heartbeat changes: **8/8 fault integration tests passed in 71.41 seconds**. Tests use real local PostgreSQL and Redis, temporary PostgreSQL schemas, test-owned TCP proxies and separately launched API child processes. They cover disconnected PostgreSQL/Redis, traffic blackholes while TCP stays open, bounded command/MULTI rejection, released PostgreSQL game-row locks, oversized MULTI queue rejection, graceful restart, abrupt process termination/restart, and a lost session-revocation notification. An accepted NO WORDS action with a 1.5-second following clock survives outages longer than 4 seconds with exact board, racks, bag, draw order and receipt preservation. Recovery resumes the game without false clock loss or extra draws. Only test-owned processes are killed; shared services are not stopped.

The health integration suite passed **12/12 tests in 897 ms**, including 20 concurrent reconciliation/checkpoint races, failed COMMIT evidence, draining races, timestamp clamps, positive post-deadline health requirements, and actual Redis `MULTI`/`DISCARD` queued replies. `npm exec tsc -- -b apps/server` passed. These are local correctness and recovery results, not Render performance or production capacity certification.

The final review reproduced an additional PostgreSQL half-open gap: after 8,532 ms a query remained pending and its transaction lock was still held despite the server statement timeout. Database configuration now has a 5-second server statement limit, an independent 8-second client read limit, and a 10-second idle transaction expiry. Transport/read failures discard the connection; other transaction errors attempt rollback with the same bounded read limit and discard the connection if rollback fails.

Three added real PostgreSQL fault cases passed individually: read timeout retires the old backend and releases its row lock; unanswered rollback preserves the original application error and retires its client; a 9-second API database blackhole preserves the accepted action and a 1.5-second game clock, then resumes without extra draws. These bring the fault file to 11 cases; a full consolidated rerun is delegated to root. The 12 health tests were rerun with the database changes and passed in 922 ms. Server TypeScript build passed.

Final resource fixes: new terminal `GAME_FINISHED` requests no longer add receipt rows, while existing successful/error receipts remain replayable and newly settled outcomes still commit. The stream delivery cache now rechecks local watcher membership after asynchronous delivery so a departing last watcher cannot leave a stale cache entry. Two new integration cases passed in 7.83 seconds: repeated terminal requests keep receipt counts fixed and preserve successful retry results; a request-triggered clock-loss settlement persists the final revision/event without a terminal error receipt. The fault file now contains 13 cases, pending root's final consolidated run. The landed authentication user-row locking/password-version checks and bounded per-socket subscription queue were independently reviewed and close the reported races.
